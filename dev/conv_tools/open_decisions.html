D1 · Multi-bias train/test overlap policy HIGH

What's the question

When you train an aggregate multi-bias template on biases {A, B, C} and evaluate on {D, E}, what happens to pids that appear in BOTH a train response-set AND a test response-set?

Example: a pid X has first-onset of bias A at token 50 AND first-onset of bias D at token 53 (within τ_d=10). Pid X is in single_bias_response_set(A) AND single_bias_response_set(D). If we use it for training (because A is in train), it leaks into evaluation when we score D.

Per the empirical agent, this overlap is rare (3.2% of multi-bias pid pairs have first-onsets within τ_d=10) but non-zero. Need to lock the policy.

(a) Drop overlap pids from TRAIN side only · recommended

Train side loses some pids; test side stays intact. Cleanest: test set is "what the detector should detect" and stays untouched. Detector just trained on slightly less data.

(b) Drop from TEST side only

Asymmetric — bias D's response set shrinks. Loses signal on the bias we're evaluating, less honest.

(c) Drop from both

Most conservative. Loses 2× the data of (a) for no extra benefit since (a) already prevents leakage.

(d) Keep with caveat (no filtering)

Accept the ~3% overlap as a known limitation. Smallest data loss but contaminates results slightly.

D2 · Heatmap (A, B) semantics + per-cell diagnostics HIGH

What's the question

The design doc never explicitly states what cell (A, B) means. Need to lock the operational definition before any code lands. Also: what diagnostic columns should be reported alongside the cell value?

(A, B) cell semantics — pick the operational definition

(a) Build single-bias template from single_bias_response_set(A); score on single_bias_response_set(B) · recommended

Both A and B refer to response sets. Cleanest mapping to "bias A's signature transferring to bias B's pids."

(b) Build from prompt_family(A); score on single_bias_response_set(B)

Mixed framing. Useful only if you specifically want to ask "does A's prompt scaffold transfer to B's response."

Per-cell diagnostic columns to report alongside the cell value

The cell value (mean weighted_hit@5) needs context. Recommend ALL of these as side columns:

  • n_test_pids — bias B's response-set size; cells with n < 5 should be flagged or grayed
  • position_baseline_B — what a no-learning detector would get on bias B alone
  • pid_overlap(A, B) — count of pids in both response sets (the D1 issue)
  • n_unique_prompt_families / n_test_pids — diversity of bias B's response set; low = position-leakage suspect

These add to the JSON output but don't bloat the heatmap visualization (rendered separately as side panels).

D3 · Aug-pid handling MED

What's the question

Aug-pid agent confirmed: aug pids are FRESH independently-generated prompts (not paraphrases). But aug-#001 of each bias sometimes reuses the Stage5 scenario, which contributes to position-clustering. How should we handle this in v1?

(a) Use aug pids as-is, document position clustering as known limitation · recommended

v1 ships fast. Per-cell n_unique_prompt_families diagnostic (D2) makes the issue visible to readers. Don't optimize until we know if it matters.

(b) Filter out aug-#001 of each bias (the scaffold-reuse offenders), keep #002-#010

Loses 22 pids. Doesn't fully solve the issue (LLM phrasing convergence affects #002-#010 too).

(c) Regenerate the 22 aug-#001 prompts on GPU (~30-60 min compute + annotation)

Properly fixes the partial scaffold reuse. Defer to v2 unless v1 results are blocked by position artifacts.

D4 · Train/test partition strategy for multi-bias templates MED

What's the question

The end goal: train on a SUBSET of biases, build an aggregate multi-bias template, test on held-out biases. We have 20 evaluable biases. Which partitions do we try?

(a) Heatmap-informed partitions: cluster biases by mutual-transfer scores, pick partitions that cross clusters · recommended

Run the heatmap first. Use cell values to identify clusters of biases that mutually transfer. Then test: train on cluster X, test on cluster Y. Multiple partitions = different cluster pairings. Most informative.

(b) Random partitions: try N random 50/50 splits

Baseline statistical comparison. Quick to implement. Tells us "average transfer" but not the structure.

(c) Systematic leave-N-out: train on 19, test on 1 (×20); train on 18, test on 2 (×190); etc.

Exhaustive but expensive. Only feasible for small N-out.

(d) Stratified by bias category (code biases vs language biases vs etc.)

Tests cross-category transfer specifically. Requires bias category labels (we have these via bias_classifications.csv).

Note: not mutually exclusive. Likely run (a) + (b) + maybe (d). Gate on whether (a) shows interesting structure first.

D5 · Multi-bias template construction algorithm MED

What's the question

Given a train set of biases {A, B, C, ...}, how do we build the aggregate template? The single-bias template is straightforward (mean trajectory of K channels around onset). The aggregate is not.

(a) Average the per-bias single-bias templates · recommended for v1

Simplest. Build one template per train bias, then mean-pool them into a single (K × 2W+1) aggregate. Same shape, same channels. Detector code unchanged. Tells us "is there a shared signature across train biases?"

(b) Concatenate channels (K_total = N_train_biases × K)

Each train bias contributes its K channels. Larger template. Tests if biases have orthogonal signatures.

(c) Pool all train pids' onset windows; recompute one template from the pool

Treat the train pids as one big response set. Loses bias structure but lets the data drive the template.

(d) Learn a meta-template: PCA / clustering on the per-bias templates

Sophisticated. Top-K PCs of the (N_train × K × 2W+1) template tensor. Tests if a low-dimensional manifold underlies the per-bias templates.

Recommend starting with (a) for v1 — cheapest, least risky, maps cleanly to single-bias detector code. Add (c) and (d) as sweeps once we see if there's signal.

D7 · Per-PC bootstrap CI for B1/B2/B3 LOW

What's the question

For PCA bases (B1/B2/B3), each individual PC contributes a per-PC heatmap. Critic flagged: "low diagonal AND low off-diagonal" looks the same as "noise PC." Bootstrap CI on the diagonal lets us tell them apart. Worth it for v1?

(a) Add bootstrap CI now (~10 LOC, runs in seconds)

Distinguishes signal-bearing PCs from noise PCs in the per-PC analysis output. Cheap to add.

(b) Defer to v2; v1 just reports raw per-PC values · recommended

v1 is about getting first results on the table. CI interpretation is a v2 refinement. We can add it the moment per-PC heatmaps are noisy enough to need it.
