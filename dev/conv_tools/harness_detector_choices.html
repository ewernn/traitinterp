Pick: harness style + detector set

Heatmap aggregation: yes — each cell (A, B) = mean Recall@K_pid (or Recall@3, Recall@5) across test-fold pids of bias B, using detector built from bias A's training data. Averaged across 5 folds.

Bias coverage: 30 non-pervasive biases. Smallest is law_911=7 pids; largest is movies_similar=90. 3+ pids threshold moot at the bias level. Per-fold cell counts may be sparse — flag cells where n_test_pids<3.

Harness options (pick one)

A. Single-method simplest

One run = one method × one heatmap. Run sequentially per method.

  • + cleanest code, easiest to debug per-method
  • + trivial to add a new method later (copy + adapt)
  • − redundant work (each method re-loads pids, re-splits folds)
  • − harder to keep configs aligned across methods

~30 min to scaffold; ~10 min/method after.

B. Multi-method shared infra recommended

One harness, methods registered as plugins. All methods share fold splits, dedup, eval. Single comparable table out.

  • + apples-to-apples by construction (same folds for all methods)
  • + one config dict per method; one CLI to run them all
  • + shared scaffolding cuts repeated code
  • − more upfront work; plugin interface needs design

~45 min to scaffold; ~15 min/method after.

C. Tune-then-evaluate most rigorous

Explicit 3-way split: train / tune / test. Hyperparameters (e.g., K traits, layer choice, α blend) selected on tune fold. Locked configs evaluated on test.

  • + kills the α=0.25 contamination bug fully — every hyper picked on tune
  • + paper-grade methodology; reviewers can't object
  • − less data per split (train ~65%, tune ~15%, test ~20% of groups)
  • − nested loops slow it down ~2-3×

~75 min to scaffold; ~25 min/method after.

D. Bootstrap/CI on top of A or B stretch

Re-run a chosen harness with multiple seeds (10-50). Report bootstrap CIs on every cell + overall.

  • + honest uncertainty estimates (not just SEM-across-folds which understates)
  • − 10-50× compute; only worth it for the final paper-table run

~15 min add-on after A/B works; tens of mins to hours of compute.

My pick: B (multi-method shared) for the development run, then add bootstrap-CI from D for the final paper-table. Skip C for now: hyperparameters are mostly fixed defaults (the only one that needed tuning, α blend, applies only to the cohort-template method which we may not even ship as the lead — and we already have its main hyper, K_traits, set per the agreed cohort design).

Output structure (what the harness produces)

For each (method × metric) combination:

  • Heatmap: 30×30 cells (off-diagonal = transfer; diagonal = within-bias held-out). Cell value = mean Recall@K_pid across test-fold pids of bias B, averaged over 5 folds.
  • Diagonal summary: per-bias within-bias recall (sanity — does the method work on its own bias?).
  • Off-diagonal summary: mean transfer recall across all (A≠B) cells; max transfer; "best target B for each A".
  • Aggregate per-method: mean of diagonal, mean of off-diagonal, ratio (the "shared signature" indicator).

Output dir: dev/conv_tools/cross_bias_eval/{method}/{metric}/heatmap.json + summary.md
